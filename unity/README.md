# Immersa Unity (visore Quest 3)

Progetto Unity SEPARATO dall'app web: niente qui dentro tocca `src/`, `supabase/` o il deploy Cloudflare.
Punto di ritorno dell'app web: tag git `web-pre-unity` (`git checkout web-pre-unity`).
Per abbandonare Unity basta cancellare la cartella `unity/` (e il branch).

## Regole
- Package Android diverso dal web: `app.immersa.quest.unity` (si installa accanto all'APK web, non lo sostituisce).
  Non usare `immersa-apk\android.keystore` finché non si decide di sostituire l'APK web; per i test va bene la keystore di debug.
- Supabase: stesse tabelle e stesso bucket del web, nessun cambio di schema. URL e chiave anon in un file locale
  ignorato da git (`Assets/Config/Local*`), mai nel repo.
- Logica pura (layout, misure, allineamento) in C# senza `UnityEngine`, testabile con `dotnet` (cartella `Core/`, da creare).
- Commit di tutto (inclusi i `.meta`) prima di ogni sessione col ponte MCP: ogni modifica si annulla con git.

## Creare il progetto (una volta, lo fa l'utente)
1. Unity Hub → New project → **Unity 6 LTS** → template **Universal 3D (URP)** → nome `Immersa` →
   posizione: la cartella `unity/` di questo repo (se Hub crea una sottocartella `unity/Immersa`, spostane il contenuto in `unity/`).
2. File → Build Profiles → Android → Switch Platform. Player Settings: Scripting Backend **IL2CPP**, ARM64,
   Minimum API 32, Package Name `app.immersa.quest.unity`.
3. Window → Package Manager: installare Meta XR All-in-One SDK (o Meta XR Core + Interaction + MR Utility Kit) e
   Unity OpenXR Meta; poi `com.unity.nuget.newtonsoft-json` e glTFast.
4. `git add unity && git commit` e push sul branch di lavoro.

## Ponte MCP (strada 2, dopo il punto 4)
Da fare su Claude Code locale nella cartella `unity/`; i passi esatti si verificano sulla documentazione del pacchetto scelto.

## Logica pura in C# (`Assets/Scripts/Core/`, scritta dalla chat cloud)
- Cartella della chat cloud: la sessione locale la USA ma non la modifica senza chiedere (se serve un cambio, dirlo all'utente).
- Niente `UnityEngine` lì dentro; i tipi `Vec2/Vec3/Quat` sono i nostri (assi del WEB: three, destrorso, y su). La conversione verso Unity (z invertito, quaternioni) si fa in UN solo posto, al bordo con Unity (da scrivere quando serve).
- Fatto: `Vectors.cs`, `Types.cs` (= `src/room/types.ts`, i campi sconosciuti si conservano in `Extra` per non perdere dati di una versione più nuova del web), `Json.cs` (camelCase, campi assenti non scritti), `Places.cs` (= `src/room/places.ts`). `Assets/link.xml` evita che lo stripping IL2CPP tolga i campi letti da Newtonsoft.
- Test: `dotnet run --project unity/Tests/Core.Tests` (richiede .NET 8 SDK; nessuna dipendenza da Unity). Gli stessi file li compila Unity: alla prima apertura Unity crea i `.meta` (da committare) e va controllata la Console.
- `Geometry.cs` (`P2`, rotazioni come three: `Rot`), `Structures.cs` (parte geometrica di `structures.ts`), `Measure.cs` (= `src/room/measure.ts`: dimensioni, distanze dalle pareti, facce dei muri e piani della scansione). Test: gli stessi di `measure.test.mts` + confronto con 25 stanze casuali calcolate dall'app web (`Fixtures/measure-golden.json`, si rigenera con `npx tsx docs/test-plans/gen-measure-golden.mts`).
- NOTA sul web (non toccato): in `gapsOfSolid` il confronto esatto `(pa - t) * (pb - t) > 0 || pa === pb` dà risultati che dipendono dall'ultimo bit quando gli spigoli dell'oggetto hanno la stessa proiezione, cioè quando si misura lungo gli assi dell'oggetto (stanza senza pareti/progetti in spazio libero): un raggio può partire dal lato sbagliato e dare una distanza falsa. Il C# usa una tolleranza (1e-9) e dà il risultato geometricamente giusto; per questo i confronti con il web delle distanze sono fatti solo con gli assi della stanza. Da correggere anche nel web quando si vuole.
- `Anchors.cs` (= `src/room/anchors.ts`: i 2 angoli suggeriti e l'allineamento dai due punti toccati; `Alignment` = stessa convenzione di `align.ts`): test a mano + confronto con 25 stanze irregolari del web (`Fixtures/anchors-golden.json`, `npx tsx docs/test-plans/gen-anchors-golden.mts`). Nota: in un rettangolo le due diagonali sono uguali e il web sceglie in base al rumore dell'ultimo bit; il C# prende la prima, il risultato è equivalente per l'allineamento. `SuggestCorners` non fa cache (il web sì, per scansione): chi la chiama tiene il risultato.
- `Layout.cs` + `Floor.cs` (= `src/room/layout.ts` e `floor.ts`): pose (`Pose`, `Compose/Invert/Relative`), collegamenti tra stanze con la fiducia provvisorio/confermato/a mano (`LearnedLinks`, l'orologio si può passare per i test: `nowMs`), `PlaceByLinks`, `PlaceAround`, `LinkSummary`, `RoomContains`, `PlanModelMoves`. `OrderedMap` = la Map del web (l'ordine conta: vince il primo che combacia). Test a mano + confronto con 30 mondi casuali e 70 sequenze di misure calcolati dal web (`Fixtures/layout-golden.json`, `npx tsx docs/test-plans/gen-layout-golden.mts`; tutti i rami di `learnedLinks` sono coperti). Nell'app Unity i collegamenti vanno in `rooms.scan.links` (stesso JSON), quindi le stanze imparate dal visore Unity le vede anche l'editor web e viceversa.
- `Annotations.cs` (= `src/room/annotations.ts` + `wrapLines` di `measureView.ts`): nuove note e metri, etichette, nomi, cosa disegnare (`ToMeasures`: croci, filo dell'asterisco, linea del metro, scala della nota), copia, e l'andare a capo delle etichette (max 8 righe). Test a mano + confronto con 60 annotazioni e 80 testi calcolati dal web (`Fixtures/annotations-golden.json`, `npx tsx docs/test-plans/gen-annotations-golden.mts`). Restano nel solo visore/web (si scrivono con Unity, non con la logica pura): disegno delle linee e delle etichette, gesti per creare/spostare note e metri, modalità del metro (`cycleAnnotMode`).
- `ModelParts.cs` + `Mat4.cs` (= `src/room/parts.ts`): i COMPONENTI di un modello. Il percorso salvato dal web (`"0/2"`) conta i figli nell'albero di oggetti che fa GLTFLoader di three, NON i nodi del file: una mesh con più primitive diventa un gruppo con una mesh per primitiva e i nodi figli vengono DOPO quelle mesh. `PartTree.Build(JObject gltf)` rifà quell'albero dal solo JSON del GLB (la chunk JSON si legge dall'intestazione del GLB), poi `PathOf`, `NodeByPath`, `PartFromMesh` (clic = componente, di nuovo = il padre), `GltfNodeOfPath` (da percorso a indice del nodo glTF: -1 = radice o singola primitiva di un gruppo, in Unity è un solo renderer: usare il nodo sopra), `PartName`, e `Apply(parts)` che calcola Position/Rotation/Scale dei nodi spostati (stesso ordine e stesso pivot del web; riporta a posto quelli non più modificati). In Unity: costruire l'albero dal JSON, `SetCentring(CentringOffset(box))` (il web mette sulla radice lo scostamento che centra il modello e lo appoggia a y=0), chiamare `Apply(model.parts)` e riversare i risultati sui GameObject dei nodi con `GltfNode >= 0`, nel sistema di assi del web → Unity (una sola funzione di conversione). Pivot: `PivotOf` usa i box dei POSITION (min/max) se sono float; con posizioni quantizzate/meshopt il box non c'è e il chiamante passa il pivot con `SetPivot` (dai bounds dei Renderer: stesso valore, centro in x/z e minimo in y del componente nella posa del file, nel sistema del modello). Limiti: camere/luci/istanze nel glTF non sono contate (il web le conterebbe), i nomi doppi non hanno il suffisso `_1` di three, una mesh condivisa da più nodi è trattata come copie. Test: 3 a mano + confronto con 25 file glTF casuali caricati dal vero GLTFLoader (albero, percorsi, scelta del componente, centratura, pivot, due modifiche di fila con taglio/scala non uniforme nei genitori: `Fixtures/parts-golden.json`, `npx tsx docs/test-plans/gen-parts-golden.mts`).
- Prossimi da portare, se servono: `align.ts` (probabilmente non serve in Unity: ci sono le ancore e MRUK), `textures.ts` (meglio file precalcolati)
